# Арсенал как система способностей — проект движка

Заказ дизайнера 13.08.2026: сделать так, чтобы в карту арсенала можно было
вложить **почти любую фичу**, меняющую правила или дающую игроку новые
возможности, и чтобы **бот в любой момент мог осмотреть свой арсенал** и решить:
когда эта карта мне нужна, что она даст, можно ли строить план в расчёте на неё.

Это не про карты — это про устройство движка. Ниже проект; реализация идёт после
согласования, шагами из раздела «Порядок перехода».

---

## 1. Что сломано сейчас

Пассивка карты — это **строка-идентификатор**, которую движок ищет вручную в том
месте, где она должна сработать:

```java
if (Passives.hasPassive(state, seat, "buildings_plus1_hp")) { ... }
```

Отсюда три беды, и все три подтверждены ревизией 13.08.2026:

1. **Пассивка может «существовать» и не работать.** Из 29 пассивок колоды 1.2.0
   три не написаны вовсе, а три написаны обёрткой, которую никто не вызывает
   (`market_second_kelium_full`, `retaliation_strikes_first`, `plus1_storage_cell`).
   Карта в колоде, бот на неё рассчитывает, эффекта нет. Ничто в коде не мешает
   этому повториться: забыть вызов — норма, проверить забытость нечем.
2. **Новая фича = правка движка в неизвестном числе мест.** Чтобы добавить
   «авиабаза требует на энергию меньше», надо найти все места, где считается
   требуемая энергия. Их может быть три, а можно найти два.
3. **Бот не знает, что у него на руках.** У него есть скорер, где для каждой
   пассивки вручную вписано число «сколько это стоит». Ни о времени, ни об
   условиях, ни о связи с планом речи нет. Незнакомая карта = случайное число.

## 2. Идея: способность как ОБЪЯВЛЕНИЕ, а не как код в движке

Способность (`Ability`) описывает себя тремя вещами:

- **КУДА** она вмешивается — список **точек правил** (`hooks`);
- **КОГДА** она срабатывает — постоянно, по СПЕЦ-действию или на событие;
- **ЧТО ДАЁТ** — и для движка (изменение значения/разрешения), и **для бота**
  (машинно-читаемая подсказка ценности).

```java
public interface Ability {
    String id();                       // "airbase_needs_one_less_energy"
    Trigger trigger();                 // PASSIVE | SPEC | ON_EVENT
    Set<Hook> hooks();                 // куда вмешивается
    /** Постоянное вмешательство: правит значение правила. */
    default void modify(RuleQuery q) { }
    /** СПЕЦ/реакция: делает ход. */
    default boolean apply(GameState s, int seat, Agent agent) { return false; }
    /** Самоописание ДЛЯ БОТА (см. §4). */
    Hint hint();
}
```

**Точки правил (`Hook`) — закрытый перечень.** Это те места, где движок вообще
готов слушать способности. Первый набор, покрывающий всю диктовку:

| Группа | Точки |
|---|---|
| Сборка | `assembly.energy_needed` · `assembly.units_out` · `assembly.ammo_out` · `assembly.pay_energy_with_coin` |
| Стройка | `build.zone` · `build.price` · `build.free_move_building` · `build.unit_with_building` |
| Движение | `unit.speed` · `movement.free_extra` · `movement.jump_over` |
| Бой | `attack.ammo_cost` · `attack.range` · `attack.targets` · `attack.protect_hex` · `combat.second_battle_surcharge` · `combat.retaliation` |
| Жетоны | `token.hp` · `token.return_to_reserve` |
| Энергия | `energy.sources` · `energy.swap_cost` · `energy.income` |
| Приказы | `order.block_bypass` · `order.bottom_actions` · `order.spec_count` |
| Хранилище | `storage.cells` · `storage.holds_trophy` |
| Экономика | `market.rates` · `science.pay_with` · `refresh.income` |
| Очки | `scoring.vp_source` · `scoring.vp_modifier` |
| Поле | `field.add_spawn_tile` · `field.forbid_hex` |

Движок в каждой такой точке **спрашивает** реестр:

```java
int need = RuleQuery.of(state, seat, Hook.ASSEMBLY_ENERGY_NEEDED)
                   .base(building.energySlots)
                   .ask();                       // способности правят значение
```

Правило движка: **никакой `hasPassive("...")` вне реестра.** Если способности
негде вмешаться — значит нужна новая точка, и она добавляется осознанно, а не
россыпью условий.

### Почему это лечит именно найденные беды

- **Мёртвая пассивка становится невозможной:** тест обходит все зарегистрированные
  способности и проверяет, что каждая объявленная точка **хоть раз спрашивается**
  движком за прогон партий. Способность, чью точку никто не спрашивает, валит
  сборку. Именно этот тест поймал бы все шесть сегодняшних дыр.
- **Новая фича = данные + один обработчик** в реестре, без поиска по движку.
- **Карта, чью точку движок ещё не умеет спрашивать, честно помечается `inert`**
  автоматически: реестр знает, реализована ли точка, и Setup изымает такие карты
  сам, без ручных пометок в YAML.

## 3. Три карты из диктовки на этом каркасе

**«Лёгкий взлёт» — авиабаза требует на энергию меньше.**
Точка `assembly.energy_needed`, триггер PASSIVE, `modify`: `q.add(-1)` если здание
— авиабаза. Двух мест в движке не бывает: точка одна.

**«Резервный штаб» — сжечь келемий, чтобы обойти блокировку приказа.**
Точка `order.block_bypass`, триггер SPEC, `apply`: списать келемий, снять урезание
верха на этот ход. Движок и так знает про совпадение — теперь у этого знания есть
внешний вход.

**«Наводчик» — дальность 2 при авиации на гексе.**
Точка `attack.range`, PASSIVE, `modify`: `q.max(2)` если на гексе-источнике есть
своя авиация. Бой спрашивает дальность в одном месте, значит и правка одна.

## 4. Как бот ЗНАКОМИТСЯ со своим арсеналом

Главная часть заказа. Способность обязана рассказать о себе так, чтобы бот не
нуждался в написанном вручную числе.

```java
public record Hint(
    Bottleneck relieves,   // какое узкое место снимает: ENERGY, AMMO, COINS,
                           // KELIUM, UNITS, REACH, TROPHY, ACTIONS, VP
    double strength,       // насколько сильно, в единицах этого ресурса за раунд
    Horizon horizon,       // NOW | THIS_ROUND | REST_OF_GAME
    Precondition needs,    // что должно быть на столе, чтобы это заработало
    boolean oneShot) { }
```

И один вход для бота:

```java
List<Review> Arsenal.review(GameState s, int seat);

public record Review(
    String cardId,
    boolean usableNow,        // условия выполнены и СПЕЦ свободен
    String blockedBy,         // словами: «нет авиации на гексе», «нет монеты»
    double valueNow,          // польза, если разыграть сейчас
    double valueIfHeld,       // польза, если додержать до подходящего момента
    String enablesPlanStep) { // шаг ПЛАНА, который эта карта расшивает
```

Как считается ценность — без ручных чисел на карту:

1. **Узкое место плана.** У бота уже есть слой `Plan` (цель + шаги). Каждый шаг
   знает, чего ему не хватает: энергии, боеприпасов, войск, досягаемости. Если
   `Hint.relieves` совпадает с нехваткой текущего шага — ценность умножается.
2. **Проверка условия.** `Precondition` считается по состоянию: не выполнено —
   `usableNow = false`, и бот видит **почему** (это же попадёт в метрики словами).
3. **Держать или играть.** `REST_OF_GAME` пассивка тем ценнее, чем раньше
   поставлена (успеет отработать больше раундов) — но занимает слот. `NOW`
   утиль-эффект тем ценнее, чем острее сейчас нехватка. Бот сравнивает
   `valueNow` и `valueIfHeld` × вероятность, что нужный момент наступит (по числу
   оставшихся раундов).
4. **План строится В РАСЧЁТЕ на карту.** `enablesPlanStep` — обратная связь в
   `Plan`: цель, недостижимая без карты, становится достижимой с ней, и бот может
   выбрать эту цель, планируя разыграть карту на нужном шаге. Это ровно то, что
   ты просил: «могу ли я строить стратегию, опираясь на способность, которую
   разыграю позже».

Скореры пассивок с вписанными от руки числами после этого удаляются: их заменяет
единая оценка через `Hint` + план. Незнакомая карта перестаёт быть случайным
числом.

## 5. Метрики выпадают из той же системы

Раз каждый розыгрыш и каждое вмешательство идут через реестр, запись метрик — это
**одно место**, а не правки по всему движку. На каждую карту за партию пишется:
вышла ли в игру, сожгли ли верх, поставили ли низ, осталась ли в руке, а для
розыгрыша — **ситуация словами**, взятая из той же `Precondition`/`Bottleneck`
(«не хватало энергии», «был бой рядом», «армии нет»). То же самое ложится на
задания: выполнено обычным требованием, усиленным, сожжено ради верха, не
выполнено — и в какой ситуации.

## 6. Порядок перехода (без остановки работы)

1. **Каркас:** `Hook`, `RuleQuery`, `Ability`, `Hint`, реестр `Abilities` и
   тест-обходчик «каждая точка спрашивается». Поведение игры не меняется.
2. **Перевод существующих 29 пассивок** на реестр по одной, с тестом на каждую.
   Здесь же закрываются шесть найденных дыр.
3. **Точки под диктовку:** скорость и здоровье, энергия Сборки, зона стройки,
   дальность и защита в бою, обход блокировки, ячейки хранилища, доход в
   Обновление, модификаторы очков.
4. **`Arsenal.review` и связь с `Plan`;** удаление рукописных скореров пассивок.
5. **Метрики** по картам и заданиям, отчёты по наборам.
6. **Полная колода из диктовки** — уже без правок движка на каждую карту.

Шаги 1–2 не добавляют игре ничего нового, но именно они делают всё остальное
дешёвым: после них новая карта — это данные плюс один обработчик, а «карта есть,
а эффекта нет» становится невозможным по построению.
