# Заказ: цифровая версия «Кристаллов Раздора» — hot-seat, сетевая игра, боты, полный лог партии

**Дата:** 16.08.2026
**Кому:** агенту/чату, который будет это реализовывать (без доступа к текущей сессии —
документ самодостаточен).
**Основания:** движок игры уже существует и обкатан массовыми симуляциями (см. §2).
Это заказ на НАДСТРОЙКУ над существующим движком, а не на игру с нуля.

---

## 1. Идея и приоритет

Автор хочет три режима игры на одном движке:

1. **hot-seat** — одна партия, один компьютер, один клиент, игроки передают
   устройство по кругу (или сидят за одним экраном);
2. **сетевая игра** — несколько клиентов, локально в сети или через интернет,
   реальные люди на разных компьютерах играют одну партию;
3. **боты в реальной партии** — любое место за столом можно отдать существующему
   боту вместо человека, в любой комбинации (см. §2.3).

**Важнейшее уточнение автора, которое меняет приоритет всего заказа:**

> «Важно учесть главное — в этом приложении самое ценное — это не возможность
> поиграть, а это логи партии. Которые покажут полностью всё для чёткого видения
> того, как можно играть в игру. Там должна быть вся инфа: сид ботов, какое поле,
> какая сборка из блоков, у кого что на старте. Затем все ходы, все карты в руках,
> вся информация и действия в каждый момент времени партии.»

Из этого следует порядок приоритетов, и он **обратный интуитивному**:

- **Приоритет №1 — ПОЛНЫЙ ЖУРНАЛ ПАРТИИ.** Не «лог для отладки», а исчерпывающая
  запись: сид генерации, раскладка поля и сборка блоков, стартовые условия каждого
  игрока, и затем — абсолютно всё, что происходило, на любой момент партии,
  **включая скрытую информацию** (все карты на руках у всех игроков, а не только
  того, чей ход). Это инструмент дизайнера для изучения того, как реально играется
  игра — такого же типа, для чего уже построен `KeliumReplay2` (см. §2.4), но
  источником теперь служат НАСТОЯЩИЕ партии (люди, сеть, боты), а не только пакетные
  симуляции.
- **Приоритет №2 — сама возможность сыграть** (hot-seat / сеть / боты) —
  обязательна, но она существует ПОТОМУ, что нужны настоящие партии, которые дадут
  содержательные логи, а не только как самоцель «поиграть».

**Практическое следствие для архитектуры:** движок должен писать полный журнал
партии **всегда, для любого режима**, одним и тем же способом, что и в
симуляциях — сохраняя ЖУРНАЛ ВЛОЖЕННЫМ ПОВЕРХ ЖИВОЙ СЕТЕВОЙ ИГРЫ отдельно от того,
что реально увидели игроки в моменте (см. §5 про разделение «честного» и
«полного» представления).

## 2. Что уже есть в движке — читать перед реализацией

Репозиторий: `backskin/forged-in-kelium` (Maven, 4 модуля:
`engine ← cards ← bots ← gui`, зависимости строго однонаправленные). Не
переизобретать нижеперечисленное.

### 2.1. Точка входа в партию

```java
kelium.engine.GameEngine.playGame(GameState state, List<Agent> agents,
    Consumer<Map<String,Object>> onEvent)
```

Это ЕДИНСТВЕННАЯ точка запуска партии. `state` строится через
`kelium.engine.Setup.buildGame(config)` (конфиг несёт версию свода правил, раскладку
поля, число игроков, сид). `onEvent` — колбэк, вызываемый на КАЖДОЕ игровое событие
(ход, действие, бой, награда, обломок и т. д.) — это и есть источник данных для
журнала партии из §1.

### 2.2. Контракт агента — точка входа для UI/сети

```java
public abstract class kelium.core.Agent {
    public final int seat;
    public final String name;
    public abstract Choice choose(GameState state, List<Choice> options, Map<String,Object> context);
    public void observeEvent(Map<String,Object> event) { }        // только "свои" события
    public void observePublicEvent(Map<String,Object> event) { }  // ВСЁ, что происходит за столом
}
```

Движок в каждой точке решения формирует список ДОПУСТИМЫХ `Choice` и спрашивает
агента, какую выбрать (`context.kind` различает вид решения: `"reveal_order"`,
`"action"`, `"combat_source"`, `"combat_target"`, `"build_pick"`, `"move"` и т. д.).
Это уже готовая архитектура «точек выбора» — **именно через неё** подключается и
бот, и (что нужно построить) реальный человек за экраном:

- бот — существующие `Agent`-реализации, выбор решается внутри `choose()`
  синхронно, без ожидания;
- **человек за интерактивным клиентом — НОВЫЙ класс `Agent`**, которого в
  репозитории СЕЙЧАС НЕТ: его `choose()` должен не вычислять решение, а
  **блокироваться**, отправить клиенту (локальному окну — в hot-seat, или по сети —
  в сетевой игре) текущее состояние и список `options`, и ждать, пока
  игрок/сетевой клиент не пришлёт выбор.

**Важное предостережение:** в модуле `bots` есть `kelium.agents.HumanLikeAgent`.
Несмотря на название, это **бот, симулирующий человеческую неидеальность**
(добавляет шум в решения, чтобы бот играл «как живой человек» в тренировочных
матчах) — это НЕ заготовка для реального интерактивного ввода и не годится как
основа для нового Agent из предыдущего абзаца. Путать их нельзя.

### 2.3. Боты, которых можно посадить за стол

`kelium.agents.Bots.create(String character, int seat, Random rng, int players)` —
фабрика готовых характеров (`hawk`, `dove`, `balanced`, `opportunist`, `explorer`,
`chaos`, `warlord`, `axiom`, `reaper` и др., полный список — в `Bots.java`).
Дать пользователю на сетевом/hot-seat столе посадить бота на любое место — это
вызов уже существующей фабрики, без нового ИИ-кода.

### 2.4. Уже существующий инструмент для журналов — не строить логи с нуля

`gui/src/main/java/kelium/gui/GameRecorder.java` и весь пакет
`gui/src/main/java/kelium/gui/replay2/` (`BoardWindow`, `BoardSheet`, `CardReader`,
`Chart`, `Drawer`, `MarkIcons`, `Metrics`, `ModuleSlot`, `OrdersTable`, `Timeline`,
`RulesBook`/`HelpBook` и др., ~19 файлов) — это уже построенный формат записи и
СУЩЕСТВУЮЩИЙ Swing-проигрыватель партии: показывает поле по раундам, планшеты
игроков, ленту времени, разбор ходов, метрики. Он уже умеет визуализировать именно
то, что требуется в §1 — но сейчас питается только от пакетных симуляций.

**Что нужно от этой части заказа:** не переписывать `replay2` заново, а (а) убедиться,
что формат записи, которым пользуется `GameRecorder`, действительно фиксирует
ВСЁ требуемое из §1 (сид, раскладку/сборку блоков, старт каждого игрока, и далее —
полную историю, включая закрытые карты на руках у всех), и при нехватке —
расширить формат записи, а не выдумывать новый; (б) сделать так, чтобы партии из
hot-seat, из сети и партии с ботами точно так же писали эту запись, как сейчас пишут
её симуляции; (в) сам просмотр журнала может остаться в `replay2`/Swing либо
переехать в веб-клиент (см. §4) — это решение реализатора, лишь бы данные были
идентичны.

## 3. Требование №1 — полный журнал партии (реализовать в первую очередь)

Журнал партии должен содержать, без сокращений:

1. **Сид партии** (тот, что передан в `Setup.buildGame`/`GameConfig`) — партию
   можно детерминированно воспроизвести.
2. **Версия свода правил и всех каталогов карт** (`GameConfig` уже несёт версии
   ruleset/objectives/containers/arsenal/boards — писать как есть, дисциплина
   версионирования уже есть в проекте: версии контента иммутабельны, см. §6).
3. **Раскладка поля и сборка из блоков** — конкретный `.kmap`/board id и фактическая
   геометрия поля партии (гекс-координаты, тип блоков-контейнеров и т.д.).
4. **Стартовые условия каждого игрока**: характер (бот/человек), стартовая позиция,
   стартовые ресурсы/склад, стартовая рука заданий (`objectiveHand`), любые другие
   параметры старта.
5. **Полная хронология партии** — на любой момент времени должно быть видно:
   - чей ход, какой раунд/фаза;
   - все действия всех игроков (что выбрано в каждой точке `Agent.choose`, не
     только победивший вариант, но и то, какие `options` вообще предлагались —
     это тоже ценная информация «как можно было сыграть иначе»);
   - **карты в руках у ВСЕХ игроков в любой момент** (задания, приказы, арсенал) —
     это скрытая от других игроков во время реальной партии информация, но
     журнал для дизайнерского разбора обязан её содержать целиком (см. разделение
     представлений в §5);
   - все события боя, наград, обломков, трофеев, победных очков по источникам —
     `onEvent`-поток уже несёт всё это, писать его целиком, не фильтровать.
6. Журнал пишется **для партии в любом режиме одинаково** — hot-seat, сеть, бот-vs-бот
   — один и тот же формат, чтобы `replay2`/аналитические инструменты работали
   без разбора «откуда партия».

Реализация: подписать `onEvent` в `GameEngine.playGame` на пишущий приёмник
(расширение/аналог того, что уже делает `GameRecorder`), плюс явно зафиксировать
в записи то, что сейчас в события НЕ попадает — полные закрытые руки на каждый
момент (например, снимок `state` целиком раз в фазу, а не только события).

## 4. Требование №2 — hot-seat и сетевая игра

### 4.1. Архитектура (рекомендация, не догма)

Раз партия должна быть воспроизводима и по сети, и локально — правильно держать
**авторитетную симуляцию (движок) в одном месте**, а клиенты — только
показывают состояние и шлют выбор:

- **hot-seat**: один процесс на одном компьютере, движок и все `Agent`
  (человеческие и ботовские) живут в нём же; переключение хода — это просто смена
  того, чей интерфейс сейчас активен на экране (скрывать чужие закрытые карты между
  передачами устройства — иначе «полная информация для текущего хода» из требования
  автора превратится в подглядывание за чужой рукой).
- **сеть**: движок и `GameEngine.playGame` выполняются на СЕРВЕРЕ (авторитетно,
  чтобы клиент не мог жульничать/расходиться состоянием); каждый клиент подключается
  по сессии/партии, получает: (а) публичное состояние стола, (б) СВОЮ закрытую
  информацию (свою руку), видит запросы `Choice` только когда очередь его агента,
  и отправляет обратно выбранный `Choice`; боты на сервере — обычные `Agent` без
  сетевого клиента вообще.
- Оба режима запускают ОДИН и тот же `GameEngine.playGame`, различие только в том,
  что стоит за интерактивным `Agent.choose()` — локальный UI-поток (hot-seat) или
  сетевое ожидание ответа клиента (сеть).

### 4.2. Новый компонент — интерактивный `Agent`

Единственный принципиально новый серверный класс: `Agent`, чей `choose()`:

1. Сериализует `state` (публичную часть + собственную закрытую руку места
   `seat`) и список `options` в сообщение клиенту;
2. Дожидается ответа (по сети — с таймаутом/переподключением, см. §4.4);
3. Возвращает выбранный `Choice`.

### 4.3. Фронтенд — что игрок должен видеть для своего хода

Автор явно требует: на экране должна быть видна **вся информация, доступная
игроку для принятия решения прямо сейчас**. Минимальный список того, что уже можно
прочитать из `GameState`/`CardContext` и обязано попасть на экран:

- своё поле зрения на игровое поле (гексы, войска, здания, контейнеры, кто где стоит
  — как минимум то, что уже рисует `FieldView`/`BoardsPanel` в существующем GUI);
- свой планшет: ресурсы/склад, наличные жетоны, здания;
- свою руку приказов (played/unplayed), руку арсенала (в руке и установленный),
  руку заданий — и **для каждого задания на руке — прогресс и что ещё нужно**:
  это уже готовая функциональность движка карт (`CardContext`/`Objective.progress()`
  и `.needed()`, модуль `cards`), просто вывести её в интерфейс, не пересчитывать
  заново;
- видимую (публичную) информацию по другим игрокам: их поле, их видимые здания/войска,
  их количество карт на руке (без содержимого), их видимые ПО/счёт;
- список легальных `options` для текущей точки решения — тех же самых, что движок
  прислал в `choose()`, а не придуманных заново на клиенте.

Технология фронтенда не диктуется этим заказом — решение принимает реализатор.
Единственное жёсткое требование: раз нужна сетевая игра между разными компьютерами
(не только локальная сеть, но и «через интернет с друзьями»), клиент должен по
крайней мере МОЧЬ работать без локальной установки JVM/Swing на стороне каждого
игрока — это довод в пользу веб-клиента (браузер) как минимум для сетевого режима;
hot-seat может как переиспользовать тот же веб-клиент локально, так и остаться на
существующем Swing-стеке — на усмотрение реализатора, но дублировать один и тот же
интерфейс на двух технологиях без причины не стоит.

### 4.4. Сетевой бэкенд — минимальные требования

- **Лобби/сессия партии**: создать партию (выбрать раскладку, число игроков,
  версию правил — те же параметры, что уже принимает `GameConfig`), пригласить
  игроков по коду/ссылке, назначить места людям и ботам.
- **Авторитетность**: сервер — единственный источник истины по `GameState`;
  клиент никогда не мутирует состояние напрямую, только шлёт `Choice`.
- **Переподключение**: если игрок теряет соединение посреди партии, партия не
  должна разваливаться — сервер ждёт (с разумным таймаутом) переподключения того же
  места; журнал партии (§3) при этом продолжает писаться без разрывов.
- **Что НЕ входит в этот заказ**: аккаунты/логины, платежи, модерация чатов —
  не запрашивалось, не делать.

## 5. Разделение «честного» представления и «полного журнала»

Это ключевое архитектурное решение, вытекающее из §1:

- **Во время живой партии** (hot-seat между передачами устройства; сеть — всегда)
  каждый клиент видит ТОЛЬКО то, что положено по правилам: свою закрытую руку и
  публичную информацию по столу. Это не опция, а обязательное условие честной игры
  против других живых людей.
- **Журнал партии** (записывается сервером/движком параллельно, независимо от того,
  что в моменте видели клиенты) содержит ВСЁ, включая закрытые руки всех игроков в
  любой момент времени — как уже сказано в требовании автора. Доступ к полному
  журналу — это отдельный, постигровой (или дизайнерский/наблюдательский)
  режим просмотра, а не то, что течёт живым игрокам во время партии.

Не путать эти два потока данных и не давать полному журналу просачиваться в
интерфейс живого игрока во время его собственной партии — иначе это подглядывание
в чужие карты.

## 6. Дисциплина версионирования и переиспользование данных

Проект уже держит строгую дисциплину: файлы версий правил/каталогов карт
(`data/rulesets/*.yaml`, `data/cards/objectives.*.yaml`, `containers.*.yaml`,
`arsenal.*.yaml`, `boards/*.yaml`) **иммутабельны после создания** — любое
изменение создаёт НОВУЮ версию, старая не редактируется. Цифровая версия игры
обязана читать те же файлы данных, что и движок/симулятор, тем же
`GameConfig`/`Setup.buildGame`, не заводить свой параллельный источник контента.

## 7. Явно НЕ входит в этот заказ

- Переписывание боевого ИИ ботов, обучение, балансировка карт — это отдельная,
  уже идущая линия работы, не относится к цифровизации.
- Правка текста правил/устранение противоречий в СВОДе — отдельная задача.
- Мобильные приложения, магазины приложений, монетизация — не запрашивалось.

## 8. Порядок реализации (рекомендация)

1. Журнал партии (§3) — расширить существующий формат записи `GameRecorder`, если
   он не покрывает всё требуемое; проверить на партиях бот-vs-бот (это не требует
   ничего нового в интерактивности, самый дешёвый и самый ценный первый шаг —
   он же и приоритет №1 автора).
2. Интерактивный `Agent` + минимальный hot-seat клиент на одном процессе, без сети —
   доказать, что человек может реально сыграть партию через `choose()`/`options`,
   видя всё нужное по §4.3, и что журнал при этом пишется идентично симуляции.
3. Вынести авторитетную партию на сервер, добавить сетевой транспорт и
   лобби/сессии (§4.4), тот же клиент, что в п.2, подключается по сети.
4. Дать сажать ботов `Bots.create(...)` на любые места в hot-seat и сетевой партии.
