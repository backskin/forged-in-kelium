### Что УЖЕ есть (проверено в этой сессии — движок заданий РАБОТАЕТ)

Механика заданий реализована полноценно, это НЕ надо писать с нуля:
- `java-sim/src/main/java/kelium/engine/Objectives.java` — ядро:
  - `playableObjectives()` — какие задания в руке выполнимы (проверка требования
    через реестр предикатов + оплата жертвы);
  - `playObjective()` — розыгрыш: платит жертву, выдаёт base_reward всегда,
    special_reward если выполнено ещё и `enhanced` требование (награды
    складываются), удаляет карту, эмитит событие `objective`;
  - `grantBase()` / `grantSpecial()` — выдача наград (ammo/kelium/coin/trophy/
    container/module attack|assembly|storage/arsenal/objective_card).
- Верхний утилизационный эффект: `GameEngine.objectiveBurnTop()` — «сжечь верх
  карты ради мгновенного эффекта вместо выполнения низа» (реестр `Effects`).
- Реестр предикатов: `java-sim/src/main/java/kelium/engine/Predicates.java` (~45
  предикатов, включая гео sp_*). Проверено: ВСЕ предикаты, используемые в
  заданиях, зарегистрированы — «мёртвых по коду» заданий нет.
- Раздача заданий: старт 1 карта; в конце раунда +1 если строго <3 (правило);
  покупка на рынке; награда за усиление даёт свежую карту. События
  `objective_drawn` логируются (GameLogger).
- Данные: `simulator/data/cards/objectives.base-2026-08-11.yaml` — 40 обычных +
  8 стартовых + 6 новых экспансия (o41-o46) = **54 карты**. У всех есть `top`
  (верхний эффект). Формат карты:
  ```
  - id: oNN
    name: "..."
    kind: regular            # regular | starting
    type: state|incident|sacrifice
    sacrifice: {resource: ammo, amount: 4}         # только для type:sacrifice
    requirement: {predicate: <id>, params: {...}}  # базовое требование (низ)
    enhanced:    {predicate: <id>, params: {...}}  # усложнённое (доп. награда)
    base_reward:    {ammo: 3}                       # даётся всегда
    special_reward: {trophy: 2, objective_card: 1}  # если enhanced выполнено
    top: {effect: <id>, params: {...}, label: "..."} # верхний эффект (сжечь карту)
  ```

## КЛЮЧЕВОЙ ДИЗАЙН-ВЫВОД СЕССИИ (важно для дизайнера)

Пользователь хотел агрессию/войну/блокировки/«навалиться на лидера». Мы внедрили:
соревновательную оценку (мои ПО − лидер), прицел в лидера, захват зданий,
характеры агрессии, задания на экспансию, осаду ЦУ. Боёв стало больше, но
**война НЕ стала доминирующей стратегией**, и причина структурная:

**`return_destroyed_tokens = true`** (правило) — уничтоженные токены
возвращаются владельцу в конце раунда. Значит вред сопернику ВРЕМЕННЫЙ: убил его
армию — она вернулась. Поэтому нельзя «выбить из игры», и рациональный бот копит
очки наукой (безопасно). Осада ЦУ работает механически (урон копится: в
Обновление снимается 1 кубик, не весь), но невыгодна: HP ЦУ 4, реген −1/раунд.

Дизайнер решил **правило возврата НЕ менять**. Значит честный потолок агрессии =
темп + трофеи + захват ЦУ (3 ПО за жетон). Если дизайнер захочет, чтобы война
была топ-стратегией — единственный настоящий рычаг это правило возврата токенов
или крупные ПО за перманентный урон, а НЕ дальнейшая настройка ботов. Это
дизайн-развилка для будущего решения.
